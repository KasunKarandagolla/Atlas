## 3. Actual workload and configuration boundaries

**CONFIRMED from source, not an observed owner run:** [broad workset](../../src/atlas/v2/runtime/broad_universe.py) retains all observed products (<=2,048/venue), <=24 active history keys, mandatory benchmarks/watches and a <=20 same-venue research cohort. [Universe tiers](../../src/atlas/v2/data/universe.py) rank by turnover/canonical identity: Tier 2 uses `20 - mandatory_count` in the broad call, Tier 3 top 5 plus mandatory watch/position and applicable S3 keys, hard ceiling 8; four exploration slots remain. Cohort/history size is not WS subscription size.

[Stream plan](../../src/atlas/v2/data/broad_stream_source.py) selects Tier >=3 plus BTC/ETH benchmarks/watches/positions: <=16 instruments, <=8 depth keys, <=32 topics. Binance sends aggTrade for each selected key and depth@100ms only for depth keys; actual maximum 24 topics. No BBO or liquidation WS is added by that plan. Cold seeding uses available BTC/ETH; it does not prove a mature run stays at two trade-only symbols. No owner workset/watch manifest was supplied; actual future symbol count/rates remain unknown. Do not pin an easy watchlist, drop required watches or claim all-market deep coverage.

[Broad REST](../../src/atlas/v2/data/broad_public_source.py): three full Binance bulk endpoints every 10 s (bookTicker, premiumIndex, 24hr ticker), hourly metadata-age bound; <=32 requests, <=16,384 records, <=5 s acquisition. Up to two enrichment keys/cycle: with focused keys, **one focused and one broad exploration key**, four bar intervals M1/M15/H1/H4, current pages plus historical cursor pages, aggregate trades/funding/OI. This is not 10-s bar delivery for every instrument. A 20-key focus would nominally revisit each focused key about every 200 s, ignoring overlap with exploration, failures and acquisition time; this is scheduling arithmetic, not measured missed-opportunity rate. Neither slowing refresh nor declaring candle-only evaluation solves the 5-s close-arrival requirement. Timely origin/quote coverage must be measured first.

[Production](../../src/atlas/v2/runtime/production.py) prepares four history intervals across active products for each decision event, validates/indexes retained bars, builds causal features and CandidateSet. A single durable prepared M15 slot feeds [research maintenance](../../src/atlas/v2/runtime/broad_research_queue.py). [History maintenance](../../src/atlas/v2/runtime/active_history.py) advances one key/frame per eligible turn (500-ms minimum cadence), not a full-history job on every tick. Repeated preparation/validation at nearby cutoffs is a **cost hypothesis**, not measured dominant CPU. Reuse is safe only with exact immutable prefix/availability parity; R1 already permits removing redundant work, not truncating histories.

**Configuration-only:** `ResearchRunConfigV2` can select Binance, execution/providers DISABLED, data root/disk reserve, and reports 60–86,400 s. It cannot configure smaller Tier/stream caps, candle/history intervals, 10-s polling, S1/S2-only evaluation or disable built-in M1/analogue/statistical research. `provider_profile=DISABLED` prevents optional provider dispatch; it does **not** disable M0, synchronous `_run_m1`/analogue after eligible frozen actions, or the installed statistical shadow. Do not count already-idle branches as new savings.

**Value assessment:** a 10-s broad cycle adds no new closed S1/S2 candle most of the time (90 refreshes per 15M interval), but updates liquidity/eligibility, ranking, mark/funding and PIT source coverage. The broad workset explicitly requires quote-field receipts within 30 s; a 60-s substitute would violate that existing health rule. Its incremental economic value versus a separately designed timely-close/fresh-quote scheduler is unknown. Broad history is essential for warmup, scanner selection and later support, while repeatedly deriving unchanged prefixes is only candidate waste. Continuous streams preserve short-lived S3/S4 information and execution calibration; reporting itself generates no entry signal. Preserve collection while measuring avoidable recomputation, not the reverse.

Actual event delivery also needs scrutiny: public context launches one of nine default sources per 60-s round-robin turn (nominal nine-minute revisit, failures may lengthen it), while the official calendar has a separate 60-s cadence. Those are implemented acquisition schedules, not proof of immediate incident discovery or successful source coverage. Slowing them for economy could weaken the most safety-sensitive information. No claimed seconds-scale S7 capability follows from fast stream service.

**CONFIRMED ordinary-run isolation gap:** [product](../../src/atlas/v2/product.py) constructs `PublicContextMaintenanceV1` without a selected-venue source list; its [defaults](../../src/atlas/v2/news/events.py) include `BYBIT_OFFICIAL` and `BYBIT_STATUS`. Binance-only market config therefore cannot establish zero inactive-venue traffic across the ordinary shadow runtime. The commissioning path deliberately excludes that strategy/context runtime; its isolation does not qualify this ordinary path. A future bounded selected-venue context binding/rejection test is needed before a Binance-only shadow run, preserving macro/Binance/affected-asset safety. This finding authorizes no implementation here.

4. **Only then target demonstrated redundant work or report scheduling.** Immutable-prefix reuse/batched lookups are information-preserving candidates under R1, not confirmed savings. Prioritize complete-publication exclusive costs if still dominant; exclude optional research contention before another rewrite. Reduce ordinary report starts only when measured worthwhile. For any eventual C proposal, preregister a paired baseline/challenger full calendar on the same PIT instruments, seeds, costs and risk: S1/S2 timely eligible setups, watch trigger/expiry/deadline losses; S3 minute origins/VWAP error; S4 warmup/1s–30s coverage/markout; S5 confirmation latency; S6 ranks/cohort inclusion; S7 blackout/incident correctness; S8 both-leg coverage.
