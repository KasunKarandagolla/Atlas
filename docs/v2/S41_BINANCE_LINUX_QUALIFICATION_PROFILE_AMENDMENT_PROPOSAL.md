# S41 Binance single-venue qualification profile amendment

**Status:** PROPOSAL FOR COORDINATING REVIEW — not operative until accepted
**Proposed profile version:** `S41_BINANCE_SINGLE_VENUE_QUALIFICATION_V1`
**Source checkpoint:** `dcb5d9dbe6ec58ee337b29accb48f96ef174ec1d`
**Scope:** qualification profile, measurement workflow and certificate binding only

This proposal gives the owner’s Binance-only deployment a separately measured qualification path. It does not rewrite historical dual-venue results, change the public-evidence contract, or grant execution or strategy authority. Existing S41 queue, durability, chronology, 10-second polling and 1.5-second service bounds remain in force. New runs continue to use the accepted `1.0.0-research` selector contract; proposed S6 numerical action parameters stay disabled, with S6 rank/trigger/shadow evidence honestly marked unavailable for action. S7 retains its scope-limited fail-closed rules. The proposal does not claim that a Binance-only result is equivalent to dual-venue F1/F4 evidence.

## 1. Proposed profile

One immutable profile version has two independently required host targets:

| Target | Required bound | Qualification identity |
| --- | --- | --- |
| Linux development/deployment laptop | Linux; two logical CPUs allocated to ATLAS; nominal 4 GiB physical RAM; actual CPU quota, usable memory, filesystem, volume identity and canonical data path recorded | `S41_BINANCE_SINGLE_VENUE_QUALIFICATION_V1 / linux-2cpu-4gib` |
| Native Windows deployment laptop | Native Windows on the owner’s selected device and data volume; exact device/OS/runtime/resource facts recorded during commissioning | `S41_BINANCE_SINGLE_VENUE_QUALIFICATION_V1 / windows-native` |

Each host needs its own commissioning record. Linux evidence cannot admit Windows, and a CI or other-host measurement cannot admit either owner device. A source, lock, physical-format, profile, workload, host, data-volume or selected-path change invalidates the relevant certificate. Windows remains a required target even if its qualification occurs later.

The profile freezes `public_venues=("BINANCE",)`, `selected_execution_venue="BINANCE"`, `execution_profile="DISABLED"`, and `provider_profile="DISABLED"`. No Bybit reader, poller, stream lane, scanner, research job, report source, account client, DNS request or fallback may be created. A new qualification run must use its own source-bound run/workset; existing Bybit history may remain immutable but cannot be read as active research input. Any active watch, open-position/recovery item, due job or selected artifact bound to Bybit rejects startup rather than being filtered. Switching venues remains an owner action after safe stop and reconciliation, including resolution of exposure/orders/UNKNOWN; this profile performs no account access or execution and cannot attest that resolution. Any Bybit initialization or request is a terminal qualification failure.

The current `ResearchRunConfigV2` can express this configuration, but accepts one or two venues, defaults to Bybit, and the UI starts with its Bybit checkbox selected. Therefore a saved configuration alone is not adequate enforcement. The new profile must be checked by product configuration validation and the runtime factory before any source is constructed; the captured source/endpoint manifest must independently prove that only Binance ran.

## 3. Preflight and commissioning dependency

The current ordinary start path calls `preflight_run` before opening the production writer. Host-path preflight can succeed, but the broad assessment receives `S41_MAX_BREADTH_BYTES_PER_CYCLE_V2=None` and correctly returns `TEST GATE`. A normal run therefore cannot be used to create the missing measurement. Do not bypass this result or start `run_component` directly.

Use the already accepted A2 `--commission-capacity` child architecture as a **preflight phase**, with a narrow Linux owner-host extension:

1. **Bootstrap host preflight:** run the existing bounded `HOST_PATH` probe on the selected owner data root. Verify same-volume resolution for SQLite, WAL, archive, reports and temporary files. If this fails, do not start network collection.
2. **Commissioning-only child:** when the matching capacity record is absent, the product supervisor may launch the A2 commission child. It receives a structured canonical request binding `purpose=QUALIFICATION_ONLY`, the exact Binance-only profile, selected path/device, source and lock hashes, declared resource reserves and a unique disposable subdirectory below `<selected-root>/qualification/`. It cannot launch a normal research run, strategies/admission decisions, provider work, execution or credential access. It uses the existing production public source, stream plan, durable capture, `BroadPublicRuntimeV2`, sole-writer repository and read-only report path; it does not implement a second data path or new harness.
3. **Minimum live full-path check:** after the child’s own host-path check passes, collect exactly 120 measured seconds from the selected actual stream plan. This provides twelve 10-second broad cycles and two 60-second report intervals. Include concurrent broad polling, a read-only report/export overlapping publication, WAL-FULL activity, post-COMMIT observation, causal cutoff reads and 1-second resource sampling. Setup and final bounded drain use the existing deadline; retain a report for every attempt. The check writes only to the disposable qualification root.
4. **Capacity qualification:** this 120-second live check is a commissioning feasibility result, never a `BroadCapacityMeasurementV2` success or a 48-hour claim. After the proposed profile’s early single-venue F1/F2/F3/F4 engineering checkpoints pass, run the accepted A2 integrated qualification on the same host, device, selected profile and exact final source. Use the selected maximum one-venue population and the frozen capacity/fault/report protocol. The accepted A2 currently specifies a 30-minute two-venue workload and Windows commissioning only; this proposal explicitly requests versioned one-venue lane/population binding and a Linux owner-host A2 child. A2 issues a valid measurement/certificate only on complete success.
5. **Normal production admission:** rerun ordinary `preflight_run`. It must verify the certificate/report hashes, exact source/profile/host/device/path bindings, current free space, memory and CPU reserves, and the existing storage path probe. Only this ordinary successful result can admit `run_component`. The commissioning-only permission does not satisfy or override production preflight.

This two-phase admission resolves the circular dependency: a path-checked, authority-zero A2 child is permitted to generate the absent evidence as a preflight operation; the product run remains denied until a completed measurement is consumed by the unchanged fail-closed admission boundary. The 120-second result cannot be reused as the longer capacity certificate.

On Linux, retain immutable reports and the certificate under the selected volume’s `qualification/<certificate-hash>/` directory, owner-only (`0700` directory, `0600` files), with content hashes and exact profile bindings. On Windows retain the already accepted selected-volume records and DPAPI CurrentUser-protected copy. Every launch rechecks host/device/path/source/profile, certificate and report integrity, disk headroom, declared memory/CPU reserves and the <=30-second path probe. No cross-device reuse. Failure/cancellation/timeout retains diagnostics, issues no valid certificate and leaves Start disabled.

## 4. Acceptance and stop rules

### 120-second Linux live commissioning check

Pass only when all are true:

- the run manifest, loaded factories, started lanes, REST endpoint inventory and report source set contain BINANCE only; Bybit construction/request counters are zero;
- the stream plan is the exact hash of the measured Binance product/tier/watch snapshot and respects 16 instruments, 8 depth keys and 32 topics;
- every accepted raw transport frame has exact immutable identity and chronology; capture/archive evidence reconstructs byte-for-byte; interpreted public evidence is complete and visible only after complete commit and durable post-COMMIT observation;
- at each measured causal cutoff, eligible queries/export return exactly the expected committed observation-qualified rows and exclude private staging, unobserved rows, future events and late publications;
- every due 10-second broad cycle finishes within its existing cadence with complete source/missingness records; any unavailable or incomplete cycle remains visible and makes the measurement non-passing;
- accepted/captured/indexed identities reconcile after clean drain, with zero rejected or irreversibly lost frames; queue item/byte maxima and lane reservations are never exceeded; stream service gap is at most 1.5 seconds;
- no positive backlog slope over the final 30 seconds; after source stop, accepted work reaches zero within the existing clean-stop deadline;
- concurrent report/export succeeds without pinning writer/WAL progress or advancing its cursor beyond causal evidence;
- host and process CPU, RSS, RAM availability, PSI, disk write/growth, WAL, archive, transaction/fsync latency and source/queue/writer phase timings are recorded at 1-second resolution or exact operation scope, with actual producer-window timestamps and counters;
- source health remains valid for the measured scope, and there is no disconnect, sequence gap, hash mismatch, corruption, OOM, queue-loss latch or evidence ambiguity.

The live check reports exact mean/p95/max frames/s, bytes/s, trades/frame, 1-second frame and byte peaks, both Binance lane rates, queue high-water, indexed/durable rates, writer/worker exclusive timings, broad-cycle duration, report duration, resource headroom and final drain. It does not infer unsampled market bursts or endurance.

### Versioned single-venue capacity qualification

Keep existing numerical F1/F4 and A2 limits. Version the profile’s source/topology binding explicitly: F1-micro/F1 uses one active `BINANCE_MARKET` lane at 160 sustained frames/s with a 320-frame/s one-second burst; F4 uses two Binance channel lanes (`BINANCE_MARKET` and `BINANCE_DEPTH`), each 80 frames/s, with trade and depth payloads and 320 aggregate one-second bursts at 30 and 90 seconds. This tests one venue with distinct stages; it does not prove dual-venue fairness. Use the exact F1-micro trade/byte geometry for F1-micro. For F4 and A2 use the exact selected Binance plan and depth/trade geometry, bound by the live commissioning report; synthetic identities remain test-only and carry no source/economic authority.

The F1-micro gate remains >=240 observation-qualified indexed frames/s while backlogged, <=66.7-ms mean complete 16-frame descriptor cycle, <=1.5-second service gap, pre-burst backlog <=16, burst recovery <=5 seconds, zero loss/rejection, and final drain zero. Only after it passes run one full 60-second F1: producer-window indexing >=160 frames/s, mean interpretation <=100 ms, <=1.5-second service gap, final 20-second backlog slope <=0, actual burst/recovery and accepted/raw/indexed count agreement. F2 runs three full 10-second cycles at 256, then 1,024 Binance instruments, with changed/unchanged responses and mandatory universe/workset writes; each cycle must finish <=10 seconds with exact raw/locator/revision/cutoff checks and no due backlog. F3 runs three such cycles at the exact selected target (up to the existing one-venue 2,048-product limit), with no extrapolation. F4 runs 120 seconds with the two Binance channel lanes at 80 frames/s each, one-second 320-frame/s bursts at 30 and 90 seconds, <=1.5-second service gap, nonpositive post-burst backlog slope, zero loss/reject, complete drain, publication/restart and report/WAL-stall checks. The 30-minute A2 integrated gate retains 160 aggregate frames/s, declared 320 bursts, 60-second reports, 60-second storage growth windows, selected maximum one-venue breadth, and all resource/fault/restart checks. Every due broad cycle remains <=10 seconds. No smaller population, slower cadence, raised deadline or queue increase is admitted.

This is a **new one-active-venue qualification profile**. It does not pass, replace, or retroactively reinterpret any old dual-venue F1/F4 report. No statement of dual-venue fairness, simultaneous-venue capacity, or venue equivalence follows from it. Historical failed reports remain byte-for-byte unchanged in the evidence directory and validation ledger.

### Resource envelope and stop behavior

Use the accepted A2 measurement and admission equation without guessed rates. The profile’s declared disk floor must be at least the run’s existing `minimum_free_disk_bytes` (currently default 1 GiB); its CPU budget cannot exceed the measured two-core allocation. An owner RAM reserve, owner disk floor and explicit total-memory ceiling must be present in the profile; missing values block admission rather than being filled with host-wide guesses.

`required_free = ceil(1.25 * (startup_remaining + T * sum(component_max_rates) + transient_reserve)) + owner_free_floor`.

Measure each growth component once: broad raw/locators, stream evidence and trade IDs, histories/repair/enrichment, derived evidence, reports/temp files, SQLite permanent allocation and WAL high-water. Include measured pending accepted work, maximum broad cycle and shutdown/final report in transient reserve. The Linux/Windows certificate declares `owner_free_floor`, owner RAM reserve, total memory ceiling and CPU budget. Admission rejects absent/invalid declarations, insufficient disk, total declared memory above host usable memory minus owner reserve, or source/profile/host mismatch. No guessed constant or linear population extrapolation.

Preserve A2 telemetry actions: warn at 85% of declared RSS ceiling, or CPU above 85% of declared budget over a 60-second window, and when free space falls below recomputed remaining-duration need; stop at the declared RSS ceiling or 60-second CPU-budget breach, before free space reaches `transient_reserve + owner_free_floor`, on a breached service/resource envelope, or immediately on irreversible queue rejection. Stop new acquisition, retain and drain accepted work within the existing bounds, persist terminal health/receipt, and leave dependent decisions unavailable if drain/publication fails. A test that stops for pressure is failed qualification evidence, not a pass.

## 7. Unresolved assumptions and recommendation

**Verified:** source SHA is `dcb5d9dbe6ec58ee337b29accb48f96ef174ec1d`; the recovery documents agree on the frozen limits; current ordinary preflight is blocked by missing broad measurement. The sanitized Linux sample reported 2 CPUs, 3.72 GiB RAM (1.37 GiB available), ext4 with 89.3 GiB free and 77.3% host CPU over five seconds; these are host-wide observations, not ATLAS-attributed load. The five-minute Binance observer covered only BTCUSDT/ETHUSDT and did not exercise ATLAS persistence. No owner run/workset exists in the inspected default data location; native Windows and the full dynamic Binance workload have not been measured. The latest Linux investigation narrative is in `log.md`; its observer and host sample are temporary files referenced by exact hashes, not a standalone checked-in report.

**Unknown:** the actual active watch/open-position snapshot, target-selected stream symbols, measured 2-CPU/4-GiB full-path throughput/resources, owner-declared RAM reserve/CPU budget, and native Windows qualification. The prior two-symbol traffic report and 478-ms synthetic descriptor result cannot settle these.

**Recommendation — NO-GO for production qualification or ordinary run admission at this checkpoint.** Submit this versioned profile to the coordinator for approval; if approved, implement only the commissioning/preflight slice, run the 120-second source-bound Linux measurement first, and stop on its earliest failing gate. Do not issue a capacity certificate or claim the target pipeline is sufficient until the single-venue F1/F4 and A2 gates pass on the exact Linux host; qualify native Windows separately. The historical dual-venue failures remain open and unchanged, economics remains `NOT ESTIMABLE`, and capital/assisted execution stay disabled.
